# AGENTS.md

Operational guide for every coding agent in this repo (Claude Code, Gemini,
Antigravity, Codex). `CLAUDE.md` and `GEMINI.md` only import this file, so all
agents read the same rules: edit them here. For prose-level architecture see
`README.md`; this file is the agent cheat-sheet: commands, invariants, and the
non-obvious traps.

## What this is

Septena: a private, local-first task app for Apple platforms (iOS / macOS /
watchOS) backed by its own sync & MCP backend (`backend/`, ADR 0002 / ADR 0007).
Code targets still carry the working name `Septask` / `SeptaskMac` /
`SeptaskWatch` (ships as "Septena"). The life OS (Septena Life) moved out to
`michellzappa/septena-life` in ADR 0017 (`septena-life-archive` tag). SwiftUI
on iOS/iPadOS/watchOS, native AppKit shell on macOS; Swift 5.10; deployment
target 26.0.

## Build / generate

`project.yml` + XcodeGen is the **source of truth** for the Xcode project — never
hand-edit `Septena.xcodeproj` (it's regenerated). After any project change:

```bash
xcodegen generate
```

Build from CLI (the destination/scheme pattern that works here):

```bash
xcodebuild -scheme Septask      -destination 'generic/platform=iOS'     -configuration Debug build
xcodebuild -scheme SeptaskMac   -destination 'platform=macOS'           -configuration Debug build
xcodebuild -scheme SeptaskWatch -destination 'generic/platform=watchOS' -configuration Debug build
```

Schemes: `Septask` (iOS, embeds Watch + Share extension), `SeptaskMac`,
`SeptaskWatch`, and `SeptenaCoreTests`. `*.entitlements` files are
**hand-maintained** (XcodeGen references them but does not generate them) —
container / app-group / bundle-id strings live there and are edited by hand.

**Build once per logical unit, never concurrently.** Make a coherent change, then
run **one** verifying build before leaving the tree green — not after every file
touch. With 3–5 parallel sessions plus the hourly commit-cron, concurrent
`xcodebuild`/`xcodegen` against shared state corrupts incremental builds, so
**build through `scripts/build.sh`** (defaults to the iOS `Septask` scheme): it
takes a shared `mkdir` lock at `/tmp/auto-build.lock.d` so builds serialize
across every session and the cron. The compile is the only green gate before the
cron pushes — a tree that doesn't build must never be left behind.

**The iOS scheme cannot build when no watchOS simulator runtime matches the
SDK the active Xcode ships** (e.g. Xcode 26.6 ships watchOS 26.5; runtimes
installed are 26.2 + 27.0). `Septask` embeds `SeptaskWatch`, so xcodebuild
resolves a watch destination and dies — either at the scheme precondition
("watchOS 26.5 must be installed") or further down in `actool` on the
complication's asset catalog. Same mismatch, two different-looking errors,
neither self-explanatory.
**Nothing is wrong with the project** — Xcode.app builds fine because you pick a
concrete destination it can resolve. `scripts/build.sh` detects this before
taking the lock and exits 2 with guidance. When the change doesn't touch watch
code, gate it on the Mac scheme instead — it compiles the same shared sources:

```bash
scripts/build.sh SeptaskMac 'platform=macOS'
```

If the change *does* touch watch code, **stop and tell the user** — installing a
multi-GB runtime is their call, never the agent's.

**Building on mz-mini** (`remote-build`): the mini has no development
certificate, so `SeptaskMac` fails before compiling ("requires signing with a
development certificate"). Compile unsigned with `SEPTENA_NO_SIGNING=1`.
`remote-build` copies uncommitted edits too, so run it from a clean worktree
when you need to check exactly what is committed:

```bash
remote-build "xcodegen generate && SEPTENA_NO_SIGNING=1 ./scripts/build.sh SeptaskMac 'platform=macOS'"
```

**Android build and device artifact:** Android compiles through
`.github/workflows/android.yml` on `ubuntu-latest`, using Temurin JDK 17 and
the checked-in `android/gradlew` wrapper. The workflow uploads a short-lived
debug APK artifact for the user to install on a connected device with `adb`.
It does not run tests or launch the app. The mini currently has no Java runtime,
so do not use `remote-build` for Android or install toolchains unless the user
explicitly asks for that download.

**Shared Rust core (`core/`, ADR 0025):** task rules and sync decisions live
once, in `core/crates/septena-core`, with no I/O. No machine has a Rust
toolchain and agents **never install one** (no `rustup`, no `brew install
rust`, not on the laptop, not on mz-mini). `.github/workflows/core.yml` is the
build gate: push the branch and read the run. When `core/Cargo.lock` is
missing or stale, the `core-rust` job uploads the new lockfile as the
`core-lockfiles` artifact and fails: `gh run download <run> -n core-lockfiles`,
commit it, push again. `core/crates/septena-core/src/generated/registry.rs` is
generated by `node scripts/gen-registries.mjs` like the Swift, TS and Kotlin
constants. A rule that the core holds is never re-implemented in Swift,
Kotlin or TypeScript: call the core, or move the rule into it. Apps link a
**released** core (tag `core-vX.Y.Z`, then `scripts/core-pin.sh X.Y.Z`), never
a local build: `core/release/README.md`. Plan: `docs/SHARED_CORE_SPEC.md`.

**Do NOT drive the app — the user tests it.** An agent runs the compile, CI on
its PR, and cheap checks (typecheck, unit tests, lint, codegen). Never launch the app, boot a simulator, run UI tests, screenshot, or
otherwise "verify it works" — when the change is built, report it and **ask the
user to test**. And **NEVER download anything to unblock a build or test**
(SDKs, simulator runtimes, platform components, packages, tools — e.g.
`xcodebuild -downloadPlatform`) unless the user explicitly asked for that
download. If the toolchain is missing something, stop and tell the user; a
multi-GB platform download is their call, never the agent's.

Debug builds use `SWIFT_OPTIMIZATION_LEVEL: -Osize` on purpose: plain `-Onone`
makes SwiftUI/SwiftData/Observation 10–50× slower on-device. Trade-off:
step-debugging is imprecise (locals "optimized out"). For a true breakpoint
session, temporarily flip Debug back to `-Onone`.

There's no `.env`. Signing and update keys come from the optional
`Config/Secrets.xcconfig` (gitignored; template `Config/Secrets.example.xcconfig`).
The app builds fine without it.

## Versioning & changelog

Full guide: `docs/VERSIONING.md`. The rules that bite:

- **Two numbers, two owners.** `MARKETING_VERSION` (SemVer, user-facing) lives
  in `project.yml` and is **bumped by hand only when cutting a release**. The
  build number `CURRENT_PROJECT_VERSION` lives in `Config/Base.xcconfig` (NOT
  project.yml — a project-level value would override the xcconfig) and is
  **the git commit count**. Every build writes it into the built bundle's
  `Info.plist` (`scripts/stamp-built-plist.sh`, a `postBuildScripts` phase on
  every bundle target in project.yml), so device builds go up with each
  commit. The xcconfig value is only the no-git fallback, re-stamped by
  `scripts/stamp-version.sh` at archive time. Never hand-bump it; never move it
  into project.yml. Every embedded target (apps, watch, widgets, complication,
  live activity) reads `$(CURRENT_PROJECT_VERSION)`/`$(MARKETING_VERSION)` so the
  whole bundle stays version-consistent — mismatched extensions fail App Store
  validation.
- **0.9.x is the public beta on every platform (mz, 2026-11-25).** The Mac
  download ships with `scripts/release-macos.sh` from mz-mini, when mz says
  release (`docs/RELEASING-MAC.md`). The newest GitHub release must be a Mac
  release: installed copies read their update feed from it.
- **SemVer, pre-1.0.** Bump MINOR (`0.2.0`) for a batch of user-facing
  features, PATCH (`0.1.1`) for fixes-only. `1.0.0` = public App Store launch.
- **The cron keeps an `"Unreleased"` changelog entry current.** Each run,
  `scripts/changelog-stamp.sh` rewrites the single pinned `version:"Unreleased"`
  entry at the top of `changelog.json` — Claude-curated, human-readable
  highlights from the commits since the last release, carrying the live build
  number — and stamps `Base.xcconfig` to match. It self-guards against churn
  (skips when HEAD is already a refresh) and never touches released entries. So
  ordinary feature work still **doesn't** hand-edit the version or changelog —
  but the cron now does keep the unreleased notes + build number live. You just
  leave a green tree.
- **Cutting a release promotes the `"Unreleased"` entry**, one deliberate act in
  a single session (so the hotspot `project.yml` + changelog don't conflict
  across parallel sessions): in `Septena/Resources/changelog.json` rename the
  Unreleased entry's `version` → the real number + set name/summary + curate
  highlights → bump matching `MARKETING_VERSION` → `git tag vX.Y.Z` →
  `scripts/stamp-version.sh` → archive.
- **The changelog is one canonical JSON, two consumers.**
  `Septena/Resources/changelog.json` is bundled into the app (Settings ▸ About ▸
  What's New + the auto "What's New" sheet on update, read by `SeptenaCore/
  Changelog.swift` — which hides the Unreleased entry from the launch sheet via
  `latestReleased`) AND mirrored to the website at build time
  (`../septena-site/scripts/sync-changelog.mjs` → `/changelog`; both surfaces
  show the build number). **Author here, never in two places.** It is NOT
  generated from the runtime DB — that's life-data; release notes come from git.
  A highlight's optional `section` key drives its accent color on both surfaces.

## Branch & integration discipline

**Commit your own work. The committer-cron is NOT running.** This file used to
say a scheduled job commits green work on `main`, so agents need not commit. That
stopped being true: the newest cron commit is 2026-09-14, and the host has no
crontab entry, no LaunchAgent and no `auto-git-commit.sh`. Two months of sessions
that trusted this paragraph left their work uncommitted. Until the cron is
restored, **commit logically-complete, build-verified units yourself** — see
"Don't leave work uncommitted across sessions" below, which is now your job, not
the cron's. The same gap means `Config/Base.xcconfig` holds a stale build number
(the cron stamped it); `scripts/stamp-version.sh` fixes it at archive time, so
leave it alone. (Never rewrite shared history.)

**A request goes to closure** (global `~/.claude/CLAUDE.md`, "A new request:
take it to closure", 2026-11-24): a `wt/<name>` branch in a worktree off fresh
`origin/main`, push, PR, green CI, merge, deploy, report. Deployment
is continuous (mz, 2026-11-24): CI deploys the Worker from `main`
(`backend.yml`), and the site is deployed after every push to its `main`. Do
not ask first; check the Deploy job. Store releases stay mz's. That short-lived PR branch is
sanctioned; the rules below forbid long-lived forks.

**Default to committing on `main`. Do NOT create branches unless the user
explicitly asks for one.** The user never asks for branches — every stray
branch in this repo's history was agent-created, and that is exactly what caused
the divergence: each session forked a new branch off a frozen `main`, so two big
features once edited sections, MCP, `Localizable.xcstrings`, and
`CloudKitSchema.md` independently and the *same* display-name commit landed
twice. Work on `main`; commit green units directly. Avoid recreating that:

- **Integrate early.** Land green, build-verified work on `main` as you go. If a
  branch ever does exist (user asked, or mid-consolidation), merge it back the
  same session — don't let it outlive the task or fork siblings off its base.
- **Don't leave work uncommitted across sessions.** Commit logically-complete,
  build-verified units. "BUILT uncommitted" is the anti-pattern that caused the
  divergence — uncommitted trees are also lost to crashes.
- **Rebase before you build on top.** If a feature depends on another branch's
  work, rebase onto it (or onto latest `main`) first, don't develop blind.
- **Hotspot files conflict constantly** because every feature appends to them:
  `Localizable.xcstrings` / `InfoPlist.xcstrings` (string catalogs),
  `CloudKitSchema.md` (the deploy changelog), `project.pbxproj`. Conflicts here
  are almost always **union merges** (keep both additions; renumber changelog
  rows). Frequent integration is the real fix — they drift in proportion to how
  long branches live.
- **When asked to consolidate branches**, first map each with
  `git rev-list --count main..<b>` / `<b>..main`, dry-run merges with
  `git merge-tree`, and confirm a deleted branch's content isn't unique before
  dropping it (a stale branch's work is often already redone on `main`).

**Running parallel sessions? Use git worktrees, not one shared tree.** The user
typically runs 3–5 agent sessions at once, Claude and Gemini/Antigravity both
(Gemini takes more of the work when the weekly Claude credits run out). In a
single working tree they silently clobber each other's files (no conflict, no
warning — just lost work).

**Before you edit or commit in `~/Dev/septena` itself, check it is yours.** Run
`git status`: the branch must be `main` and no rebase, merge or cherry-pick may
be in progress. If another agent's operation is in progress, never touch it (no
`add`, `checkout`, `rebase --continue/--abort`, `stash`). Do your work in a
worktree instead: `scripts/wt-new <name>`, or for a small docs change
`git worktree add --detach <dir> origin/main`, commit, `git push origin
HEAD:main`, then `git worktree remove <dir>`. On 2026-11-21 a Claude session's
`git add` landed inside a Gemini rebase this way. One worktree
per session fixes it structurally: separate working dir (no file collisions) and
separate path-keyed DerivedData (no build contention). Use the helpers:

```bash
scripts/wt-new <name>     # creates ../septena-<name> on a short-lived wt/<name> branch
#  …work the session in that dir, build with scripts/build.sh, commit on the branch…
scripts/wt-done <name>    # green-gated merge back to main (build the MERGED tree,
                          # finalize + push only if green, else abort), then cleanup
```

The `wt/<name>` branch is the **sanctioned exception** to "no branches" precisely
because `wt-done` merges it back the *same session* and deletes it — that's the
opposite of the long-lived forks that caused the divergence. Hotspot files
(`*.xcstrings`, `project.pbxproj`, `CloudKitSchema.md`) still conflict at merge;
that's the *good* failure mode — a conflict you resolve (union merge) beats a
silent clobber. `wt-done` refuses to merge a dirty main or an uncommitted worktree;
commit on the branch first (or let the cron do it).

## Architecture invariants (do not violate)

- **Mutators are the write boundary.** Views and App Intents must not write
  SwiftData entities directly when a mutator exists (`TaskMutator`,
  `AreasMutator`, `ProjectsMutator`). The mutator does the optimistic local
  update, queues the change for the task backend, saves context, and posts the
  right notifications.
- **There are no sections.** The life OS (sections, plugins, dashboards,
  HealthKit and provider imports) left in ADR 0017. It lives in
  `michellzappa/septena-life` and under the tag `septena-life-archive`. Do not
  add section code, life-OS copy or a link to Septena Life.
- **Undo is ONE shared stack** (`SeptenaCore/TaskUndo.swift`), wrapping a single
  process-wide `UndoManager`. Every task surface points at it — the AppKit
  table, the SwiftUI lists, and iOS shake / three-finger undo (the app
  delegates override `UIResponder.undoManager`, the last stop in the responder
  chain, so a focused text field still wins for typing). **Record explicitly at
  the user gesture, never inside a mutator**: the mutators also run for
  backend applies, the 30-day purge, recurrence spawning, and the watch, so
  recording there would put sync traffic on the undo stack and let ⌘Z "undo" an
  edit another device made.
- **Read `DayClock.today` / `DayClock.now` in views**, never `Date()` directly —
  this is what makes day rollover work.
- **App Intents must `await SeptenaServices.shared.start()` before mutating**
  (they can run background-launched).
- **The app does not use iCloud.** It syncs with `api.septena.app` through
  `TaskSyncEngine` (ADR 0002). `CKEngine` never starts; it remains only because
  the mutators still take it as a parameter. Do not build on it.

## The Septask targets

The product is Septena; the code targets keep the working names `Septask` (iOS),
`SeptaskMac` and `SeptaskWatch` (`docs/SEPTASK.md`).

- **Shared folders own behavior; the root owns composition.** `SeptenaCore`,
  `Septena/Shell/Tasks`, `Shell/Sidebar` and `Shell/UI` hold task behavior for
  iOS and Mac. `Septask/` holds the app entry, launch, settings shell, root
  navigation and the AppKit shell, never task business logic.
- **Never copy a task file into `Septask/` to tweak it**: copies drift.
- **No new `#if SEPTASK`.** The condition is always set in the app targets. It
  stays in `project.yml` only until the last open branch that uses it lands.
- **After touching shared code, build `Septask` and `SeptaskMac`.** The compiler
  catches type-level seams, but NOT the runtime one: a shared view reading a
  new `@Environment(X.self)` crashes at launch if a root forgot to inject it.
  Add it to `septenaSharedEnvironment` (`Septena/Shell/UI/SharedAppEnvironment.swift`).
- **Keep the `Septask` and `SeptaskMac` source lists in `project.yml` in
  lockstep.**
- The Septask icon is generated, not drawn: recipe in `docs/SEPTASK.md`
  ("Icon Notes").

## Known traps (from prior sessions)

- **macOS keyboard & focus in a `NavigationSplitView`** (a concrete case of the
  "use standard SwiftUI, never get creative" rule under Conventions): unmodified
  keys (Return, arrows) and `.onKeyPress` / unmodified `.keyboardShortcut` are
  **focus-scoped** — they only fire in the column that holds key focus, and the
  **sidebar holds it by default**, so a detail-pane `.onKeyPress(.return)` never
  fires until the detail claims focus (the "Return triggers the sidebar" trap).
  Only **modifier** menu commands (`⌘X`) are global (why `⌘T`/`⌘K`/`⌘R` work).
  Worse, **Space** in a selected row activates the row's first button — the
  checkbox — so a bare Space *completes the task* (do not bind Space; keep the
  checkbox `.focusable(false)` so it can't be Space-activated). Standard fixes
  only: native `List(selection:)` for selection + arrow nav (never hand-rolled
  tap-gesture selection — it suppresses native keyboard nav and the List's
  click-to-focus); `@FocusState`+`.focused()` to claim detail focus; **modifier
  menu shortcuts** for every keyboard action on the selected row (rename = `⌘R`,
  complete = `⌘K`, move = `⌘M` / `⌘⇧M`); double-click / right-click for mouse.
  Do NOT bind unmodified Space/Return. The shared shortcut map is
  the registry (`registry/actions.json`, `RegistryActions.shortcuts`): every
  context menu, swipe and menu-bar item on both shells renders from it through
  `RegistryMenuResolver` (`Septena/Shell/UI/RegistryMenu.swift`); a shell only
  binds action IDs to handlers. Bare `⌘M`
  is intentionally reclaimed by the focused task list; bare `⌘.` remains the
  system Cancel equivalent and carries a `⇧` here.
  **Two sanctioned exceptions on the task surfaces** (both deliberate,
  documented, and NOT to be "fixed" back to the naive form):
  1. The deep task lists do NOT use native `List` — they use
     `SelectableScrollList` (`Septena/Shell/UI/SelectableScrollList.swift`), a
     `ScrollView`/`LazyVStack` that re-earns native selection + arrow-nav
     (reusing the canonical selection token, reclaiming focus on release, never
     binding Space) *because* it can host inline-editable content that a native
     `List` can't. Native-`List` surfaces (sidebar, Next) keep the pure-native
     path via `ListKeyboardNavigation`. So "never hand-rolled tap-gesture
     selection" holds for native `List`; `SelectableScrollList` is the vetted
     container when a surface needs both selection AND inline editing.
  2. On iPad, row-level shortcuts ARE published via **gated hidden zero-frame
     buttons** (`rowCommandShortcutsEnabled`), the one place the "no hidden
     shortcut buttons" rule is intentionally inverted — because publishing
     `.focusedSceneValue(\.taskActions)` from a split-view detail SIGKILLs iPad
     (so those publishers stay `#if os(macOS)`).
  Otherwise the ban stands: no `NSEvent` monitors, no ungated hidden buttons.
- **Never hang `.task` / `.onAppear` / `.onReceive` off a `Group`.** A modifier
  applied to a `Group` is applied to each of the group's **children
  individually** — so a `Group` whose branches all resolve to nothing has no
  child to attach to and the modifier simply never runs. This deadlocks any view
  whose loader lives there: Septask's Next feed rendered no rows cold (no
  suggestions yet, every trio block empty, the empty row gated behind
  `hasLoaded`), so `.task` never fired, so it never loaded, so it never rendered
  rows — permanently blank below the page header, with no "Nothing here yet"
  either, and `.onReceive`/`.onChange` equally dead so nothing could recover it.
  Hang lifecycle off a container that always exists (`VStack`, `List`); Septena's
  `NextView` was unaffected only because its `.task` sits on a `List`. Verified:
  identical content fires 0 times in a `Group`, 1 time in a `VStack`. Not
  greppable (the scanner can't see what a modifier attaches to) — this note is
  the guardrail.
- **`NSTableView` batch updates apply INCREMENTALLY — never feed them
  `inferringMoves()`.** Unlike `UITableView` (all indexes relative to the
  pre-batch state), each call inside `beginUpdates()`/`endUpdates()` is relative
  to what the preceding calls left behind. A `CollectionDifference` move's
  `associatedWith` offset is in the *original* array's coordinate space, so by
  the time `moveRow(at:to:)` runs, earlier removes/inserts have shifted it and
  it grabs whichever row slid into that slot. In Septask's AppKit Today list
  this moved the *group header* instead of the task — the task rendered under
  the wrong heading and read as a duplicate, with neighboring titles offset
  (surviving rows keep their cached cells and aren't re-fetched, so nothing
  self-corrects). Use a **plain** `difference(from:)` and apply
  remove+insert; that's exactly what the incremental batch is defined for, and
  a row changing groups should leave and arrive anyway. Enforced by the
  `appkit-inferring-moves` lint rule.
- **A `.plain` row Button is only tappable where it draws.** `.buttonStyle(.plain)`
  (and the plain-derived `PlainHoverRowButtonStyle` / `InertButtonStyle`) opts the
  row out of the list cell's tap target, so SwiftUI hit-tests the drawn label
  only: the `Spacer()` and every trailing gap are dead zones, and a tap near the
  right edge of the row silently misses. The row still *looks* full width, so it
  reads as "the app ignored my tap". Fix: `.contentShape(Rectangle())` on the
  label (`LogRow` carries one, which is why log rows in drawers are fine). Two
  cases need no shape — a label with its own opaque `.background(…)` fill (that
  shape is hit-testable), and a default-styled Button inside a `Form`/`List`
  (the cell supplies the target). Enforced by the `row-dead-zone` rule
  (`scripts/lint-row-tap-targets.py`, run from `scripts/lint-design.sh`).
- **No inline `TextField` swapped into a *selectable* native `List` row.**
  Replacing a row's `Text` with a focusable `TextField` (then removing it) on
  edit corrupts a native `List`'s focus/selection on macOS — after the edit ends,
  clicks stop selecting, ↑/↓ die, and the field's selected text lingers. Every
  focus workaround just moves the breakage (claim focus → dead clicks; don't →
  orphaned focus after edit). So on macOS, **task title editing happens in the
  composer** — expand-in-place inline (in `SelectableScrollList`, which tolerates
  the field) or the drawer inspector — never a raw `Text`→`TextField` swap in a
  row, and native-`List` surfaces (sidebar) rename via an alert/the composer.
  Inline-edit-in-row is fine on iOS (no split-view focus war) and fine for a
  *non-selectable* dedicated row (the quick-add line).
- **A rolled-back save looks exactly like "the user typed nothing" — never
  purge on that evidence alone.** `StoreHealth.save` rolls the context back
  when a save fails, so the write is discarded and the row keeps its old
  value. For an inline-create draft that old value is the empty title it was
  born with (`mutator.create(title: "", deferPush: true)` — the row exists,
  with an id, before the user types). The fold then read the store, saw no
  title, and called `mutator.purge` — a hard delete, no trash entry. The task
  the user had just typed was destroyed, and nothing said so. This is the
  "saving inbox items is flaky" report.
  **The rules, all four purge paths:**
  1. Mutator writes report their result. `TaskMutator.update`,
     `TasksBackend.update` and `commitAndPush` return `Bool`
     (`@discardableResult`, so plain field writes keep their shape). Any caller
     that DESTROYS a row on the strength of a write must check it.
  2. Purge needs evidence the user typed nothing, not just an empty store.
     On macOS read `KitComposerCell.pendingTitle` — the field contents survive
     a rolled-back save. On iOS gate the host's `onVanish` on `draft.canSave`.
  3. A path that cannot ask the write (the iOS filter-change sweep runs a
     runloop later) consults `mutator.lastWriteFailed(id:)` and fails CLOSED.
  4. Register an undo entry only after the write lands. An undo for a
     rolled-back rename claims it can restore a title that was never replaced.
  A wrongly-kept blank row costs one ⌘⌫. A wrongly-purged task is gone. Bias
  every ambiguous case toward keeping the row.
  No `scan` rule: the defect is the ABSENCE of a guard near a `purge` call, and
  a line regex cannot see that. Most of the seven `.purge(id:)` call sites are
  a legitimate user-initiated Delete Permanently, so a rule that flagged them
  all would just collect `septena-lint:allow` comments. This note is the
  guardrail, same as the `Group` lifecycle trap above.
  **A rolled-back save now reports itself.** `StoreHealth.noteSaveFailure`
  mirrors into `StoreHealthState.shared` (`@Observable`), which drives two
  surfaces in `Septena/Shell/UI/StoreHealthNotice.swift`: `.storeHealthAlert()`
  at the moment of loss, and `StoreHealthSettingsSection` for the running count
  (Septena ▸ Advanced ▸ Data Tools; Septask ▸ Settings ▸ Account). Both render
  nothing while the count is zero. It is an alert, NOT the `SeptenaToastStore`
  snackbar — that is a one-line auto-dismissing confirmation with an Undo, and
  a lost write is neither confirmable nor undoable, so a notice the user can
  miss would just reproduce the original complaint. Septask's Mac shell is pure
  AppKit with no SwiftUI view to hang a modifier on, so it observes
  `StoreHealthState.failureNotification` and raises the same words as an
  `NSAlert` sheet, guarded against stacking (a wedged context fails every save
  the same way).
  Related, still open: `deferPush` means a new row is local-only until the
  first title write, so a crash in that window leaves a titleless task.
- **A stored `@Model` property must not reuse an `NSManagedObject` method
  name.** SwiftData sits on Core Data, so the name collides at runtime with no
  compile error. `entity` broke fetch predicates (SQL generation threw), and
  `entityName` made reads trap after a save (Core Data's own method shadowed
  it). Before you add a stored name, check
  `NSManagedObject.instancesRespond(to: NSSelectorFromString("name"))` for the
  getter and the setter. Enforced by the `model-reserved-name` lint rule
  (entity, entityName, objectID, description, isDeleted,
  managedObjectContext, isFault, hasChanges).
- **Never build every task to read a few.** `LocalCache.allTasks` /
  `liveTasks(in:)` build a row object for each live task, logbook included,
  and each one decodes JSON. Every task change makes the open list, both
  sidebars and the area page read the store again on the main actor, so a
  whole-store read there runs on every tap and grows with the user's
  history. Pick by id with `liveTasks(ids:in:)`. Count from
  `liveAggregateEntities`. Read rings through `projectCompletionRatios`
  (memoized). Fetch Today and its band once with `todayAndTriage`. Never read
  the store in a view `body` or `init`. The full rules are in
  `docs/LAUNCH_PERF.md` ("Interaction performance"). The id-lookup form is
  enforced by the `whole-store-id-lookup` lint rule. The rest is not
  greppable, so this note is the guardrail.
- **AppKit does not load a collapsed split-view pane.** A view controller in a
  collapsed `NSSplitViewItem` has no view until the pane first opens, so its
  stack views are empty. `NSStackView.setCustomSpacing(_:after:)` raises for a
  view that is not in the stack. AppKit swallowed the exception inside event
  handling: the app stayed alive, with a menu bar and no window (2026-11-24:
  `SeptaskKitInspectorController.show` during the shell window's `init`).
  `SeptaskApp.init` now registers `NSApplicationCrashOnExceptions`, so an
  exception ends the Mac app with a crash report, as on iOS and Android.
  Guard every entry point that is called from outside the pane with
  `isViewLoaded`, hold the state, and apply it in `loadView`. Not greppable;
  this note is the guardrail.
- **No launch or load state without an exit.** A gate or spinner must end on
  success, failure and timeout. Android's first-run gate waited on a sync with
  no limit; the watch lists kept their spinner after a failed fetch. Bound the
  wait, and show the failure with a Try Again.
- **A deep SwiftUI view type overflows the iOS main-thread stack at launch.**
  The crash is `EXC_BAD_ACCESS` in `swift_getTypeByMangledName`, before any
  view draws. `TaskListView.taskListRows` hit it: a large `@ViewBuilder`
  `switch` nests every branch into one generic type. The fix type-erases each
  branch with `AnyView`. Keep large `@ViewBuilder` switches shallow, or split
  the branches into their own views. macOS has a larger main stack, so a Mac
  build that runs does not prove iOS is safe. Not greppable; this note is the
  guardrail.
- **iOS aborts on a menu shortcut that UIKit already owns.** A SwiftUI command
  with ⌃⌘S collided with UIKit's own Show Sidebar and crashed at launch and on
  typing. A shortcut the platform reserves stays inside `#if os(macOS)`. Before
  you add a `.keyboardShortcut` to a command that iPad also compiles, check the
  system menu for the same keys. Not greppable (the collision depends on the
  platform's menus); this note is the guardrail.

## Conventions

- **Use standard, default SwiftUI. Never get creative.** Reach for the
  first-party, idiomatic API every time — `List(selection:)` for selection and
  arrow-key nav, `@FocusState`/`.focused()` for focus, `.onSubmit` / a focused
  `TextField` for inline editing, `.commands` + a *modifier* `keyboardShortcut`
  for global keys, native `.contextMenu` / `.swipeActions`, `NavigationSplitView`
  for sidebar+detail. If something "needs" an `NSEvent` monitor, a hidden
  zero-frame shortcut button, a hand-rolled tap-gesture selection, an AppKit
  bridge, or any clever workaround to behave, **stop** — that's the signal the
  approach is wrong, not that it needs more cleverness. Prefer the platform's
  default behavior over a bespoke one even when the default is slightly less than
  what you imagined; a standard pattern that works beats a creative one that
  fights the framework (and that we then chase across sessions). When the
  idiomatic API genuinely can't do it, say so plainly and pick the closest
  standard behavior — don't invent.
- **Never write a list of instances into copy.** Importers, agents, platforms,
  lists and languages each have one canonical list (`registry/import-sources.json`,
  `capabilities.json`, `destinations.json`). Copy either says the general thing
  ("Import from other task apps") or is built from that list, with its status.
  A hand-written "Import from X and Y" goes stale when Z ships (mz, 2026-11-25).
- **Same behavior on every platform.** iPhone, iPad, Mac and Android do
  the same thing for the same feature. A platform-specific behavior needs a
  strong reason (a platform rule, a missing API, a different input device),
  written in a comment where the branch lives. "It was built that way first"
  is not a reason. When you find one platform drifting, fix it on all of them
  in the same change, or file an issue for the platform you cannot reach.
- **One selection/target language per surface — NEVER two.** There is exactly
  ONE visual treatment for "this row/item is selected, focused, hovered, pressed,
  or a drop target" on any given surface, and it is the app's canonical token
  (`Theme.listSelectionFill` via `SelectableListRowBackground`, with native
  rings suppressed by `.septenaSuppressListCellSelection()`). When a new
  interaction needs to emphasize a row (a drag drop-target, a hover, a keyboard
  focus), it **reuses that token** — it does NOT invent a second style (a
  different color, an accent fill vs. a neutral fill, an outline vs. a fill, a
  bespoke overlay, or the raw platform selection ring left un-suppressed). Two
  competing highlight systems visible on one surface at the same time (e.g. a
  blue outline on the selected row and an accent fill on the drop-hover row) is a
  **bug**, full stop — it reads as chaos. If you catch yourself adding a
  highlight, first find what the surface already uses for emphasis and reuse it.
  The three sanctioned shapes live in
  `Septena/Shell/UI/SelectionLanguage.swift` (see `docs/DesignSpec.md` §4.5):
  full-bleed `SelectableListRowBackground` for a list row, inset
  `InsetSelectionBackground` for a palette / source-list row, and
  `SelectableChip` for a chip / segment / filter. **An inset highlight on an
  ordinary list row is the "selection floating on top of the row" bug** — inset
  is only for palettes.
- **The app accent is the PLATFORM accent (decided 2026-11-19: "feel as native
  as possible").** No target sets `ASSETCATALOG_COMPILER_GLOBAL_ACCENT_COLOR_NAME`,
  so controls, toggles, menus and native selection use the system accent (the
  user's System Settings accent on macOS, blue on iOS). It used to be adaptive
  ink (black in light, white in dark); code written for that era may still
  assume ink. Selection fills are an accent WASH with normal
  ink text in the focused pane and gray elsewhere (decided 2026-11-19: the
  task app has no arbitrary section colors, so the accent can mean
  "selected") (`Theme.listSelectionFill`, `SeptaskKitTheme.listSelectionFill`),
  never a solid bar with white text. Selected chips use a **wash plus matching ink**
  (`SelectableChip` / `SelectableChipStyle`), contrast-safe for any tint in both
  appearances.
- **Motion is gated centrally — never bare `withAnimation` / `.animation(_:value:)`.**
  Use `a11yAnimate(_:) { … }` (drop-in for `withAnimation`, no environment
  needed), `A11yMotion.run` (when `@Environment(\.a11yMotion)` is already in
  scope), or `.a11yAnimation(_:value:)`. `LogCommit.swift` and
  `CommitMotion.swift` are the two documented exceptions — they gate once at the
  overlay.
- **Haptics: one vocabulary, chosen by meaning.** Call `Haptics.press /
  selection / commit / threshold / success / warning` (or `play` for a
  composed pattern) at the user gesture; never build a feedback generator at
  a call site (lint rule `haptics-direct-generator`). `.sensoryFeedback` is
  for local view state only, never task data: sync and undo change task data
  too. Table and rules: `docs/HAPTICS_SPEC.md`.
- **`scripts/lint-design.sh` enforces the above and runs from `scripts/build.sh`
  before the build lock.** A violation fails the build. Genuinely sanctioned
  exceptions get `// septena-lint:allow <rule-id>` **on the offending line**,
  with the reasoning in a comment above. Typography rules are advisory notes
  (a drift budget being paid down), not blockers. When you rediscover a
  convention the hard way, add a `scan` rule there as well as documenting it.
- **All *app* documentation lives in `docs/`.** Any new `.md` — plan, handoff,
  spec, design note, feature write-up — goes in `docs/`, never the repo root. Root
  is reserved for the canonical set only: `README.md`, `AGENTS.md`, `CLAUDE.md`,
  `GEMINI.md`, `SECURITY.md`,
  `LICENSE`, `NOTICE`, `project.yml`. Reference docs by their `docs/…` path.
- **Planning: start at `docs/README.md`.** It indexes every doc with a status
  and sets the rules: decisions as ADRs in `docs/adr/`, features as specs,
  order in `docs/ROADMAP.md`, work as GitHub issues + milestones on
  `michellzappa/septena`. Write an ADR before a spec that rests on a
  hard-to-reverse decision. Mark a superseded doc with a header; never delete
  or move it. **Septena is leaving iCloud** (ADR 0002): new specs design for
  the own backend only.
- **This repo is PUBLIC — keep only app-relevant docs here. Strategy lives in the
  Septena Starlings workspace** (`septena.starlings.work`, Docs `/strategy` and
  `/brand`, connector "Starlings: Septena"). Competitive strategy, positioning,
  messaging, the supporter model, the feature catalog and the **book**
  (`/strategy/the-instrument-manifesto`) do NOT belong in this repo. When the
  work is strategy/positioning/book copy, edit it *there*, not here. The copies
  in `../septena-site/docs/` are older; the workspace wins. App engineering docs
  (schema, design spec, plans, specs) stay public in this `docs/`;
  `docs/MAKER_IDENTITY.md` stays here too because it sources in-app maker copy.
- **Feature map of the task app:** Starlings Docs
  `/product/feature-map-septena-task-app` lists every user-facing feature of
  Septena (the Septask targets), with UI names vs code names, status per
  platform, and how features connect. Read it before you write copy, specs,
  issues or agent briefs. When you ship, remove or rename a user-facing feature,
  update its row in the same session. Code wins over the map. Status per
  platform is generated from `registry/capabilities.json` into
  `docs/FEATURE_MAP.md`; edit the JSON, then run the generator.
  (`/strategy/feature-catalog` is the older Septena Life catalog.)
- Match surrounding code: comment density, naming, idiom.
- **Maker voice & identity** (the "made by mz" story across app, site, support,
  journal) is specified in `docs/MAKER_IDENTITY.md` — pull facts and copy blocks
  from there, never invent maker claims. Every claim must trace to its data row;
  the banned list (no "late nights" etc.) is binding.
- **One MCP server: the task backend connector.** It is
  `api.septena.app/mcp`, served from `backend/src/shadow/mcp.ts` (Cloudflare
  Worker / TS). The in-app macOS server (`SeptenaCore/MCP/`) was removed on
  2026-11-21 (commit `7b101882`), and the old CloudKit gateway
  (`mcp.septena.app`) was decommissioned on 2026-11-20. Docs that still
  describe "two servers, edited in lockstep" are history. An MCP tool change
  lands in `backend/` plus the docs and skill briefs in the same change. Keep
  `backend/skill.md` and `Septena/Shell/Tasks/TasksSkill.swift` (the brief in
  Settings ▸ MCP Skills) in sync with the backend's tools. The agent loop (`tasks_claim`, `tasks_release`,
  `tasks_agent_events`, `tasks_activity`) lives in `src/shadow/agent.ts`: a
  claim needs the Durable Object's single writer, and its rules (leases, the
  human-only stop, pause, run budget) are enforced in `TaskStore`, not in tool
  code. See ADR 0008.
- **The MCP server is DUAL-ERA and must stay that way.** MCP revision
  `2026-07-28` made the protocol stateless (no `initialize`, no
  `Mcp-Session-Id`, no GET stream; version + client identity ride in
  `params._meta` and mirrored HTTP headers). The server implements it —
  `server/discover`, `resultType`, `ttlMs`/`cacheScope`, header validation
  (`-32020`), honest version negotiation (`-32022`) — **while still answering
  the legacy `initialize` handshake**, because Claude's connector and every
  existing `claude mcp add` registration still speak the old shape. Deleting
  the legacy path takes the live connector offline. The era rules and
  constants live in `backend/src/protocol.ts`.
